# AGENTS.md — guide for AI agents building or using this knowledge graph

This file is for an AI agent (or a developer moving fast) that needs to
run this indexer, query its output, extend it to a new service, or port
it to a different codebase — without re-reading every source file first.
For the human-oriented overview, see [`README.md`](./README.md).

## What this is, in one paragraph

A dependency-free Python tool that walks Java (Spring), Angular, and
React source trees with regex/text parsing (no AST) and writes the
result into a SQLite graph of two tables — `nodes` and `edges` — so
"what depends on what" is a SQL query instead of a grep-and-guess
exercise. Every run is a **full reindex**: for each enabled target, the
existing `.db` file is deleted and rebuilt from the current source,
never appended to.

## Non-negotiables

- **No CLI arguments.** `indexer.py` reads only `kg-config.env` (or
  `$KG_CONFIG_PATH` if set). Do not add argparse to it — if a caller
  needs a different scope, edit the config file (or point
  `KG_CONFIG_PATH` at a different one) instead.
- **Don't hand-edit a `.db` file.** It's fully regenerated by the next
  `python indexer.py` run; anything written by hand is lost.
- **`kg-config.env` list blocks are the only enable/disable switch** —
  a line inside `BACKEND_SERVICES_START`/`_END` or
  `ANGULAR_SUBPROJECTS_START`/`_END` with no leading `#` is indexed, a
  `#`-prefixed line is skipped. Never rename the `KEY` tokens.
- **`ROOT_PATH`, `OUTPUT_DIR`, `REACT_PROJECT_PATH`** can be overridden
  by an environment variable of the same name (used by Docker) — the
  env var wins over the file value.

## Running it

```
cd "D:\GitLab-Workspace\Knowledge Graph Generator"
python indexer.py
```

Or with an alternate config (doesn't touch the checked-in file):

```
KG_CONFIG_PATH=/path/to/other-config.env python indexer.py
```

Output lands at `OUTPUT_DIR` (default `./output`): one `knowledge_graph.db`
if `SINGLE_DATABASE=true`, else one `<service>.db` / `<angular-project>_<subproject>.db`
per enabled target.

## Graph schema reference

Two tables, shared by every language — see `kg_indexer/db.py` for the
authoritative `CREATE TABLE` statements.

**`nodes`**: `id, node_type, name, qualified_name (unique, may be NULL
only for edge target placeholders — nodes themselves always have one),
service, project_type, file_path, start_line, end_line, signature,
metadata (JSON text)`.

`node_type` values in use:
`SERVICE, FILE, CLASS, INTERFACE, ENUM, METHOD, ENDPOINT` (Java) ·
`BATCH_JOB, BATCH_STEP, BATCH_TASKLET, ASYNC_OPERATION, KAFKA_TOPIC,
DB_TABLE` (Java runtime flows — `spring_flow_parser.py`; deliberately no
separate `SPRING_CONFIG`/`SPRING_BEAN`/`KAFKA_PRODUCER`/`KAFKA_CONSUMER`
node types, see that module's docstring for why) ·
`NG_SUBPROJECT, NG_COMPONENT, NG_MODULE, NG_SERVICE, NG_DIRECTIVE, NG_PIPE`
(Angular) · `REACT_COMPONENT, REACT_HOOK` (React).

`project_type` values: `java`, `angular`, `react`.

**`edges`**: `id, source_id, target_id (NULL if unresolved), target_name
(the raw name as written in source, always present for name-resolved
edges), relation, service, metadata (JSON text)`.

`relation` values in use: `CONTAINS` (parent declares/holds child —
service→file, file→class, class→method, subproject→file, ...),
`DECLARES` (file→class/component; NgModule→its declarations[] entries;
also class→ASYNC_OPERATION for an `@Async` method), `EXTENDS`,
`IMPLEMENTS`, `DEPENDS_ON` (`@Autowired`/`@Inject`/`@Resource` field, or
Angular constructor injection), `EXPOSES` (method→ENDPOINT node),
`IMPORTS` (file→imported symbol, or NgModule→imported module),
`EXPORTS` (NgModule→exported symbol), `USES_HOOK` (React
component/hook→hook name called), `RENDERS` (React component→JSX tag
name it renders) · Java runtime flows (`spring_flow_parser.py`):
`DEFINES_BEAN` (`@Configuration` class→BATCH_JOB/BATCH_STEP/BATCH_TASKLET
bean), `HAS_STEP` (BATCH_JOB→BATCH_STEP), `USES_TASKLET`
(BATCH_STEP→BATCH_TASKLET), `RUNS` (caller method→BATCH_JOB, from
`jobLauncher.run(...)`), `ASYNC_CALL` (method→ASYNC_OPERATION, from
`CompletableFuture.runAsync`/`supplyAsync`), `PUBLISHES`
(method/class→KAFKA_TOPIC), `CONSUMES` (method→KAFKA_TOPIC, from
`@KafkaListener`), `WRITES`/`READS` (method→DB_TABLE, from literal SQL).
Every edge this parser creates also carries `metadata.confidence` —
`verified`/`inferred`/`unknown`, see the module docstring — in addition
to the base convention below.

**Resolution passes.** An edge is created with only `target_name` set
whenever the target node might not exist yet (different file, not yet
parsed). At the end of a run, `GraphDB.resolve_exact_import_edges()`
resolves Java `IMPORTS` edges by *exact* fully-qualified path match, then
`GraphDB.resolve_pending_edges()` resolves everything else by *simple
name* against a per-language registry built while parsing (scoped by
`project_type` so an Angular symbol can never resolve against an
unrelated Java class of the same name). An edge that's still unresolved
after both passes (`target_id IS NULL`) usually means the target is an
external library type, not a bug — `target_name` is kept so it stays
queryable. If a simple name matched more than one candidate, the edge's
`metadata.ambiguous_candidates` lists all of them; only the first was
used for `target_id`.

## Query cookbook

Prefer `example_queries.py`'s functions over hand-rolled SQL where one
already exists — they already join `nodes`↔`edges` correctly:

```python
from example_queries import connect, graph_summary, list_endpoints, search_nodes, get_dependencies, get_dependents, components_using_hook, cross_service_dependencies, run_sql
from example_queries import find_jobs, find_job_dependencies, find_kafka_topics, find_topic_producers, find_topic_consumers, get_topic_flow, find_async_operations, get_database_impact, get_runtime_flow

conn = connect("output/knowledge_graph.db")
graph_summary(conn)                              # counts by node_type / relation / service
list_endpoints(conn, service="core-service")      # REST endpoints for one service
search_nodes(conn, "PatientController")           # fuzzy name search, optional node_type filter
get_dependencies(conn, "PatientController")        # outgoing EXTENDS/IMPLEMENTS/DEPENDS_ON
get_dependents(conn, "PatientRepository")          # incoming, i.e. "who uses this"
components_using_hook(conn, "useEffect")           # React components calling a given hook
cross_service_dependencies(conn)                   # resolved edges crossing a service boundary
run_sql(conn, "SELECT ...")                        # raw SELECT, anything else is rejected

find_jobs(conn, keyword="PriceBook")               # Spring Batch jobs by name
find_job_dependencies(conn, "createPriceBookFromTempJob")  # job -> steps -> tasklets, who RUNS it
find_kafka_topics(conn, keyword="PRICE_BOOK")       # Kafka topics by name
get_topic_flow(conn, "POST_FINANCE_PRICE_BOOK")     # producers + consumers, cross-service
find_async_operations(conn, service="core-service") # @Async methods / CompletableFuture call sites
get_database_impact(conn, "price_book")             # who WRITES/READS an (inferred) DB table
get_runtime_flow(conn, "createPriceBookFromTempJob") # generic: any flow-relation edges touching a node
```

Direct SQL when you need something the helpers don't cover, e.g. every
endpoint under a path prefix:

```sql
SELECT service, name, file_path FROM nodes
WHERE node_type = 'ENDPOINT' AND json_extract(metadata, '$.path') LIKE '/auth/%';
```

Or "what does this Angular module declare, resolved to real nodes":

```sql
SELECT m.name AS module, COALESCE(t.name, e.target_name) AS declared, t.file_path
FROM edges e JOIN nodes m ON m.id = e.source_id
LEFT JOIN nodes t ON t.id = e.target_id
WHERE e.relation = 'DECLARES' AND m.node_type = 'NG_MODULE';
```

## Where the parsing logic lives (if you need to extend it)

- `kg_indexer/parsers/common.py` — shared helpers: directory walking
  with ignore rules, `find_matching()` (bracket/paren matcher that
  respects string literals), `split_top_level()`, `NameRegistry`.
- `kg_indexer/parsers/java_parser.py` — one file, one function per
  concern (`_parse_file` → `_parse_class` → `_parse_method`). To
  recognize a new annotation or a new dependency-injection style, this
  is the file to touch. Does **not** capture or store a method's own
  body text (only its signature/annotations/params/return type) — a
  parser that needs body text (like `spring_flow_parser.py`) has to
  re-derive it via `_find_block_end()` from the method's opening `{`.
- `kg_indexer/parsers/spring_flow_parser.py` — additive second pass for
  Spring Batch/Kafka/async/DB-table flows (see its own docstring for the
  full node/edge vocabulary and confidence model). Re-runs
  `CLASS_DECL_RE`/`METHOD_RE` from `java_parser.py` itself (imported, not
  duplicated) purely to get at method body text; resolves against the
  CLASS/METHOD nodes `java_parser.py` already created via
  `db.resolve()` on the *identical* qualified_name formula — recomputing
  that formula differently here would silently fail to attach anything.
  Runs per-service, after `java_parser.parse_service()` and before that
  service's `resolve_pending_edges()` call (see `orchestrator.py`), so
  cross-file references (mainly `jobLauncher.run()` targets) resolve
  through the *same* `NameRegistry`/pending-edge mechanism rather than a
  bespoke one.
- `kg_indexer/parsers/angular_parser.py` — decorator detection is
  regex-for-the-`@Decorator(` opener + `find_matching()` for the
  argument list, so nested object literals in `@NgModule({...})` don't
  break it. `ROOT_APP_SENTINEL` is how the workspace's own shell app
  (outside `projects/`) gets indexed — see `orchestrator.py` for how the
  sentinel is resolved to a real path.
- `kg_indexer/parsers/react_parser.py` — component/hook detection
  requires a block body (`=> { ... }` or `function ... { ... }`);
  expression-bodied arrows are intentionally not matched (see README
  limitations) to avoid false positives on non-component helper
  functions.
- `kg_indexer/db.py` — `GraphDB.add_node` dedupes purely by
  `qualified_name`; if you add a new node type, make sure its
  `qualified_name` scheme is unique per actual declaration (include the
  file's relative path unless the language already guarantees global
  uniqueness, e.g. Java's `package.ClassName`). Getting this wrong
  silently merges two distinct declarations into one node — this
  actually happened once with early Angular support (class name only,
  no file path) and was fixed; don't reintroduce it.
- `kg_indexer/orchestrator.py` — the only place that turns config
  values into filesystem paths and decides single-vs-per-target `.db`
  output. Both `resolve_exact_import_edges` and `resolve_pending_edges`
  are called here per language, scoped by `project_type` — do not call
  `resolve_pending_edges` without a `project_type` when multiple
  languages share one `GraphDB` (that reintroduces the cross-language
  false-resolution bug described below).

## Gotchas already found the hard way

- **Angular node identity must include the file path.** Class names like
  `ListComponent`/`DetailComponent` repeat across feature modules; a
  `qualified_name` of just the class name silently merges unrelated
  components into one node.
- **Cross-language edge resolution must be scoped by `project_type`.**
  In `SINGLE_DATABASE=true` mode, all languages share one `edges` table.
  Resolving by simple name without filtering on the source node's
  `project_type` will match, e.g., an Angular import literally named
  `Name` against an unrelated Java class also named `Name`.
- **Java `IMPORTS` edges need exact-path resolution, not simple-name.**
  A library import (`org.springframework.data.jpa.domain.Query`) can
  share a simple name with a local class in some other service; simple-
  name matching for imports specifically produced a large number of
  false "cross-service dependency" edges until this was special-cased.
- **`METHOD_RE`'s parameter capture (`[^)]*`) silently dropped any
  method with a nested-paren annotation on a parameter** — e.g.
  `@Value("#{jobParameters['x']}") Long x`. Since `[^)]*` cannot contain
  a `)` at all, the regex stopped at the `)` closing `@Value(...)`, the
  next required token (`throws`? `{`) didn't follow, and the *whole
  method* silently failed to match — not a partial/wrong parse, a
  complete miss. This wasn't a hypothetical: it made every Spring Batch
  `@Bean Tasklet` method in the real workspace (which all take a
  `@Value("#{jobParameters[...]}")`-annotated parameter) invisible as a
  METHOD node, which directly blocked the Step→Tasklet acceptance
  criterion. Fixed by allowing one level of nested parens in the params
  group (`(?:[^()]|\((?:[^()]|\([^()]*\))*\))*`), the same technique
  already used for annotation args elsewhere in this file. Verified
  against the real database (the method was simply absent) before
  fixing, and confirmed present afterward — don't trust "no error" as
  proof a regex captured everything it should have.
- **`re.IGNORECASE` on a whole pattern defeats a case-*sensitive*
  sub-part you specifically wrote for a reason.** The Kafka/DB-table SQL
  regexes needed case-insensitive keywords (`INSERT`/`insert`) but a
  strictly lowercase table-name capture (`[a-z][a-z0-9_]*`, on purpose,
  to reject PascalCase JPQL entity references like `select o from
  Order o`). Compiling with `re.IGNORECASE` on the whole pattern made
  `[a-z]` match uppercase too, so JPQL entities, SQL keywords like
  `PUBLIC`/`FINAL` used as CTE/schema names, and Postgres function calls
  in a `FROM` clause all leaked through as fake tables (1421 "tables" for
  one service). Fixed with scoped inline flags — `(?i:INSERT\s+INTO)`
  around just the keyword — so the character class outside that group
  stays case-sensitive. Caught by actually sampling the resulting
  `DB_TABLE` node names, not by trusting the pattern read correctly.

## Porting this to a different codebase

Everything codebase-specific lives in `kg-config.env` — `ROOT_PATH`,
`ANGULAR_PROJECT`, `REACT_PROJECT_PATH`, and the two list blocks. No code
changes are needed to point this at a different set of services, as
long as the backend services are Maven-style Java/Spring and the
Angular layout is a standard workspace (`projects/<name>/src`). If the
target codebase uses a materially different framework (e.g. plain
Express instead of Spring, or Vue instead of Angular/React), that needs
a new parser module following the same shape as the existing three
(`parse_service`/`parse_project` + `parse_subproject` returning a stats
dict, wired into `orchestrator.py`), not a config change.
